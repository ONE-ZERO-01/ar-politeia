## 二、反思：哪些做得对、哪些需要改进

### 2.1 做得对

1. **快速迭代诊断**：从发现「平坦地形能量不守恒」到定位根因，只用了 3 次实验 + 1 次代码阅读。时间线：跑 M1.1 → 怀疑 LJ → 跑 M1.1-d（平坦+无LJ）→ 仍不守恒 → **看代码** → `terrain_type=flat` 不处理 → 修复 → 验证完美。诊断纪律正确。

2. **小规模验证优先**：P0 全部用 1000-2000 粒子、5000-10000 步，单次实验 2-10 秒，70 次运行不到 5 分钟。如果一开始就用 100K 粒子，调试成本会指数增长。

3. **逐模块隔离验证**：M1.4（仅交换）、M1.8（仅热力学）、M1.1-d（仅 BBK）——每次只开一个模块，避免了多机制耦合导致的模糊结果。

4. **否定性结果如实记录**：M1.5 全线 Gini≈0 没有强行解释为"成功"，而是明确指出对称参数不产生 Gini——这对后续实验设计至关重要。

### 2.2 需要改进

1. **原计划过于宏大**：RESEARCH_PLAN.md 设计了 16 项实验（M1×11 + M2×5），但实际一个会话完成 P0（5/16）。应该将计划分解为更细粒度的「cycle」——Cycle 1 = P0 力场与热力学，Cycle 2 = P1 人口与层级，Cycle 3 = M2 对照实验。

2. **先验假设过于乐观**：
   - M1.1 验收标准"γ=0 总能量波动 <1e-4"——LJ 截断方式决定了这达不到（实测 6%）。标准需要根据代码实现精度校准。
   - M1.5 "48 组合 Gini 相图"——对称参数不产生 Gini。应该先做理论分析再设计实验。

3. **缺少本地 git 仓库**：发现 bug 时无法快速提交修复，只能 scp 到服务器。应该初始化 git 仓库并建立本地←→Zeus 同步流程。

4. **实验数据的可追溯性不够**：虽然所有实验都有目录和 config，但没有建立「实验编号 ←→ 运行时间 ←→ 代码 commit」的映射。AutoResearcher 的 `preflight` 和 `jobctl` 工具正是为此设计，但本次未使用。

### 2.3 flat 地形 bug 的教训

这是一个**典型的配置分支遗漏 bug**——不是逻辑错误，而是「某个值没有被任何 if/else 分支正确处理」。防御措施：
- 配置解析后应打印 "Terrain: <type>" 确认实际生效——但我们没注意看输出
- 应该在 `config.cpp` 中对未知 terrain_type 发出 warning

**行动**：已在 `main.cpp` 修复 flat 分支；建议后续加 `else` 默认 warning。
