## 二、核心诊断：Why stucks at "chiefdom"?

### 2.1 问题的三个层面

```
Layer 1: conquest 未触发合并
  ├─ conquest_enabled=true 且一直在运行
  ├─ 但 polity_events 中零 conquer 事件（M1.10 + M2.1 均如此）
  ├─ 假说A: conquest_base_prob=0.02 过低 → 5000 步碰不到一次
  ├─ 假说B: conquest 仅针对领主的子政体操作（需查实现确认）
  └─ 假说C: 所有政体距离 > conquest 有效范围

Layer 2: 继承自动碎裂层级
  ├─ 每代继承 loyalty 衰减 → superior 链断裂 → 政体降级
  ├─ hierarchy_repair_interval=500 → 每 500 步才修一次
  └─ 衰减 + 修复之间政体可能已经分解

Layer 3: 人口膨胀稀释层级密度
  ├─ N: 10K→55.6K (5.6×) 在 M1.10
  ├─ N/政体 ≈ 22 粒子 → 不足以支撑多层结构
  └─ 更多人口 → 更多新 formation → 更多碎片化
```

### 2.2 优先级：先让 conquest 工作

如果 conquest 从未触发合并，那么继承衰减和人口膨胀都无关（粒子首先要能聚合成大政体才能继承）。**让 conquest 触发是 P0**。

## 三、方法论系统性缺陷

### 3.1 当前工作流的三个断层

```
Plan → 设计实验 → 生成配置 → 跑实验 → 看结果
  ↑                                                        ↓
  └──────────────── 漏掉了这里 ──────────────────────┘
```

**在「生成配置」和「跑实验」之间，缺少了一步**：「参数合理性分析」。

以 M2.1 为例：
- 配置生成：50K×10K，continent 地形，全模块
- 应该分析：M1.10 已经显示 10K×5K 且 s=0——为什么 50K×10K 会不同？
- 实际行为：直接跑，然后 20h 等结果

### 3.2 「串行全跑」的反模式

`run_all.sh` 的理念是「一次提交所有实验，中间不需要人干预」。这适用于稳定参数下的参数扫描。但**在探索性研究中，每个阶段的结论必须决定下一阶段的实验设计**。

M1.10 的结论（s=0）应该立即触发分析和策略调整，而不是自动进入 M2.1。

### 3.3 缺失的反馈回路

```
应该的回路：
  跑实验 → 分析结果 → 调整参数 → 跑下一轮
   ↑                                    |
   └────────────────────────────────────┘

实际的回路：
  跑系列实验 → 全部跑完 → 一次性分析 → 发现全部 s=0
   ↑                                              |
   └─────────── 2-20h wtf wall-clock ─────────────┘
```

## 五、方法论修正（永久性）

### 5.1 「三问」政策

每次设计实验前问三个问题：

1. **小规模已验证吗？** → 如果 5K 粒子跑不出效果，10K/50K 只会更慢
2. **上一个实验的结论改变了吗？** → 如果没改变，复用而不是 scale up
3. **如果结果是否定的（s=0），下一步做什么？** → 必须在跑实验前定义 exit 条件

### 5.2 新工作流

```
Design → 小规模摸底（5 run × 30s） → 分析 ✓/✗ → 中规模验证（1-2 组参数）→ ✓ 成功 → 大规模对照
                                                    ↓
                                                ✗ 失败 → 调整维度 → 回到摸底
```

### 5.3 数据驱动，而非计划驱动

| 旧 | 新 |
|----|-----|
| «50K 粒子×10K 步，因为研究计划书这么说» | «先让 5K 粒子产生 state，再问需要多大» |
| «串行脚本跑到底» | «每阶段完成→分析→决策→下阶段» |
| «估计 6h 跑完» | «估计但立即验证——如果 3000 步还没 state 就杀» |
