2. 潜在问题一：内存布局与 Cache Miss

在 src/grid/ 实现中，如果你的粒子数据（SoA 架构）和地形栅格（Grid）访问不匹配，会产生严重的性能瓶颈。

风险：粒子在空间中是随机分布的，但地形栅格是连续存储的。在大规模并行时，每个时间步粒子都需要采样地形梯度，如果粒子跨度大，会导致频繁的内存非连续访问（Cache Miss）。

对策：建议在 TerrainGrid 中实现 双线性插值缓存，或者在区域分解（Domain Decomposition）时，确保每个 MPI 进程只维护本地及其 Ghost Cell 的地形数据。

4. 潜在问题三：MPI 动态负载不均衡（Load Imbalance）

这是你目前方案中最大的工程风险。

风险：地形和气候决定了资源的“富饶度”。随着模拟进行，粒子会自发向河谷和温润区聚集（如黄河流域、尼罗河流域）。

后果：由于你采用的是基于空间（Morton Z-order）的区域分解，某些 MPI 进程对应的地理区域会变得“极其拥挤”，而高山、荒漠区域的进程则处于闲置。

对策：你需要实现动态负载平衡（Dynamic Load Balancing）。不仅要根据空间划分，还要根据**粒子密度（Workload）**动态调整 MPI 子域的边界。

5. 初始条件加载的“冷启动”冲突

风险：你使用 HYDE 3.3 数据作为 Genesis 初始点。如果 HYDE 的人口分布点在你的地形势能面上恰好处于“不稳定性高点”（例如在某些 DEM 处理误差中，村落刚好位于斜坡），模拟一开始，粒子会因为巨大的地形梯度力产生不自然的“炸裂式”位移。

建议：在 Genesis 阶段引入一个 能量最小化（Energy Minimization） 预处理步骤，让粒子在锁定属性（w, ε）的情况下，先在当前地形下弛豫 N 步，达到微观力学平衡后再正式开始演化。
